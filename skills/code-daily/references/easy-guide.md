# code-daily 비개발자용 분석 글 가이드 (easy 모드)

독자는 **코딩을 한 번도 해본 적 없는 사람**이다. 변수·함수·데이터베이스 같은 말도 모른다고 가정한다.
목표는 독자가 글을 읽고 "이 프로그램이 무슨 일을 하고, 왜 그렇게 만들었는지"를 **자기 말로 다시 설명할 수 있게** 하는 것이다.
문법을 가르치는 글이 아니라, 프로그램이 하는 일을 머릿속에 그림으로 그려주는 글이다.

### 섹션 작성 요령

- **1~3번이 글의 핵심**이다. 비개발자 독자의 대부분은 3번까지만 읽고도 "아 그런 거구나" 해야 한다. 4번 이후는 더 궁금한 사람을 위한 부록에 가깝다.
- **2번 표**의 "프로그램 속 이름" 은 파일·함수 이름이지만, 나머지 두 칸에는 코드 용어를 쓰지 않는다.
- **3번 시나리오**는 꼭 실제 값(아이디, 숫자, 사진 이름 등)을 넣는다. 추상적 설명보다 값이 흘러가는 걸 보여줄 때 이해가 굳는다. 프로그램이 실제로 내놓는 메시지(코드 속 문자열)는 그대로 인용하면 좋다.
- **4번 부품**은 `outline.py` 함수표에서 독자에게 의미 있는 공개 함수만 고른다. `_` 로 시작하는 내부 함수, 단순 연결 함수는 뺀다.

### 독자 역할에 맞추기

요청에 "기획자", "팀장님", "디자이너", "고객사" 처럼 **누가 읽는지** 가 나오면, 그 사람은 글을 이해하는 데서 끝나지 않고 **읽고 나서 뭔가를 결정하거나 챙겨야** 하는 경우가 많다.
그래서 7번 섹션을 넣고, 1번 서두에 "이 글은 {독자}를 위해 썼어요" 와 읽는 시간을 한 줄 적는다.
역할이 드러나지 않으면(블로그 일반 독자, 가족·친구) 7번은 빼고 나머지 번호를 당긴다.

| 독자 | 7번에 넣을 것 | 함께 넣으면 좋은 것 |
|---|---|---|
| 기획자 | 코드에 자리는 있지만 규칙이 비어 있는 것(TODO), 대소문자·빈칸 처리처럼 정책으로 정할 것 | 화면에 나오는 메시지 전체 목록 표 (코드 속 문자열 그대로) |
| 팀장·의사결정자 | 실제 서비스로 쓰기 전에 필요한 것, 위험한 점과 우선순위 | 한계를 "지금 상태 / 생기는 일" 표로 |
| 디자이너 | 화면 종류, 버튼·입력칸, 상태별로 바뀌는 화면 | 화면 흐름도 (텍스트 화살표) |
| 고객·외부 사용자 | 사용자가 알아야 할 제약 (예: 비밀번호 찾기 없음) | 자주 물을 질문 2~3개 |

- 7번의 항목은 **6번 "아직 부족한 점" 과 코드에서 근거를 찾은 것** 으로만 만든다. 독자가 결정해야 할 것을 지어내면 쓸데없는 회의가 생긴다.
- 각 항목은 독자가 바로 답할 수 있는 **질문 형태** 로 쓴다: "비밀번호 최소 몇 글자로 할까요?" 처럼. 답이 정해지면 개발 쪽에서 어디를 고치면 되는지(`validate_signup` 같은 이름)를 마지막 줄에 한 번만 적어준다.

## 2. 타입을 쉬운 말로 — 번역표

code 모드로 타입을 적어둔 코드는 "무엇을 넣으면 무엇이 나오는지" 가 이미 정확히 적혀 있다. 이걸 아래 표로 번역해 4번 "넣는 것 → 나오는 것" 을 쓴다.

| 타입 | 쉬운 말 |
|---|---|
| `str` | 글자 (문장, 아이디, 파일 이름 등) |
| `int` | 정수 (개수, 횟수) |
| `float` | 소수가 있는 숫자 (점수, 확률, 0.91 같은 값) |
| `bool` | 예/아니오 (맞다/틀리다) |
| `None` / `-> None` | 돌려주는 것 없음 — 일만 하고 끝 (화면 그리기, 저장하기 등) |
| `X \| None`, `Optional[X]` | X 이거나, 없을 수도 있음 |
| `list[X]` | X 들의 목록 (줄 세운 여러 개) |
| `dict[K, V]` / `TypedDict` | 이름표 붙은 서랍장 (이름표 → 내용물) |
| `tuple[A, B]` | A 와 B 를 한 묶음으로 |
| `bytes` | 컴퓨터만 읽는 날것의 데이터 (사람 눈엔 알 수 없는 문자열) |
| `Path` | 컴퓨터 안의 파일 위치(주소) |
| `np.ndarray` | 숫자로 꽉 찬 격자 (사진도 사실 이런 숫자 격자다) |
| `PIL.Image.Image` | 사진 한 장 |
| `pd.DataFrame` | 엑셀 같은 표 |
| `torch.Tensor` | AI 모델이 다루는 숫자 덩어리 |
| `sqlite3.Connection` | 데이터 보관함(데이터베이스)과 연결된 통로 |

예:
- `login(username: str, password: str) -> bool`
  → "아이디와 비밀번호(글자)를 넣으면 → 맞는지 아닌지(예/아니오)를 알려줘요"
- `filter_dets(dets: list[Detection], conf: float = 0.4) -> list[Detection]`
  → "AI가 찾아낸 물체 목록과 기준 점수(기본 0.4)를 넣으면 → 기준을 넘은 것만 남긴 목록이 나와요"

타입이 없는 코드라면 코드를 읽고 추론해서 쓰되, 확실하지 않은 부분은 단정하지 않는다.

## 3. 비유 고르기

- 코드 전체를 **하나의 일상 장면**에 빗댄다. 후보: 식당 주문, 택배 배송, 도서관 대출, 은행 금고, 공항 보안검색, 놀이공원 입장, 우체국, 요리 레시피.
- 코드가 하는 일의 **흐름 모양이 같은** 장면을 고른다. 입력 검사 → 처리 → 저장 이면 "은행 창구", 걸러내기 → 전달 이면 "공항 보안검색 → 탑승" 처럼.
- 비유 하나를 글 끝까지 쓴다. 중간에 바꾸면 독자는 두 그림을 동시에 들고 있어야 해서 헷갈린다.

## 4. 말투와 표현 규칙

- **존댓말, 대화체** ("~해요", "~거예요"). 옆에서 친절하게 알려주는 선배 느낌.
- 문장은 짧게. 한 문장에 개념 하나만.
- 전문 용어는 **처음 나올 때 바로 괄호로** 풀어준다: "해시(비밀번호를 알아볼 수 없게 바꾼 결과물)".
- 영어 키워드는 우리말 뜻을 붙인다: `if` = "만약 ~라면", `return` = "결과를 돌려준다".
- 기호(`==`, `!=`, `>=`, `[]`, `{}`)는 말로 바꾼다: `>=` = "~보다 크거나 같으면".
- 숫자는 체감되게: "200,000번 반복" → "같은 계산을 20만 번 되풀이해요. 사람 눈엔 순간이지만 도둑에겐 엄청난 시간이 돼요".

## 5. 정확성 — 쉬운 것과 틀린 것은 다르다

비개발자 독자는 틀린 설명을 걸러낼 수 없다. 쉬운 설명이 오해를 심으면 오히려 해롭다.
- 비유가 실제 동작과 어긋나는 지점이 있으면 "다만 실제로는 ~라는 점이 비유와 달라요" 라고 짚는다.
- 코드에 보이지 않는 라이브러리 내부 동작을 지어내지 않는다. 모르면 "이 부분은 ~을 해주는 도구를 빌려 쓴 거예요" 정도로만 말한다.
- 실행 결과·화면은 실제로 실행했거나 사용자가 준 것만. 없으면 `<!-- 📸 실행 화면 캡처 넣기 -->`.
- 코드에 없는 기능을 "할 수 있다" 고 쓰지 않는다. 미구현은 6번 "아직 부족한 점" 으로.

## 6. 길이 조절

- 기본: 위 섹션 전체 (독자 역할이 없으면 7번 제외).
- "짧게", "한 페이지로" → 한 줄 요약 + 1·2·3번 + (있으면) 7번 + 세 줄 정리만.
- 파일이 여러 개인 큰 프로젝트 → 2번 표를 파일 단위로 만들고, 4번은 가장 중요한 부품 5개 이내로 제한한다. 모든 함수를 설명하면 독자는 지쳐서 아무것도 기억하지 못한다.
