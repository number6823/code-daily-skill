# code-daily — 규칙적인 코드 + 바로 올리는 포스트

세 모드가 한 흐름으로 이어진다.

```
code 모드: 타입·헤더·섹션 규칙대로 코드 작성/정리
      ↓  (규칙이 지켜진 코드는 scripts/outline.py 가 정확히 읽는다)
post 모드: 코드 뼈대 추출 → 개발자용 학습 기록 (노션·블로그)
easy 모드: 코드 뼈대 추출 → 비개발자용 분석 글 (비유·시나리오·용어 풀이)
```

규칙을 지킨 코드일수록 post·easy 모드의 함수표·구조 설명이 자동으로 정확해진다. 그래서 code 모드의 형식(헤더 첫 줄, `# ===== 섹션 =====`, docstring 첫 줄)은 취향이 아니라 **추출 규약**이다.
특히 타입 힌트는 easy 모드에서 "무엇을 넣으면 무엇이 나오는지" 를 쉬운 말로 옮기는 재료가 된다 (`-> bool` → "맞다/아니다를 알려줘요").

## 입력 받기

요청: $ARGUMENTS

| 첫 단어 / 요청 내용 | 모드 |
|---|---|
| `code`, "타입 붙여줘", "정리해줘", "규칙대로 짜줘", 새 코드 작성 요청 | code |
| `post`, "블로그", "노션", "Velog", "TIL", "포스팅", "기록" | post |
| `easy`, "비개발자도", "쉽게 분석", "코딩 모르는 사람도", "부모님/기획자/팀장님이 읽을" | easy |
| `all`, "정리해서 글까지" | code → post 순서로 둘 다 (비개발자용이라는 말이 있으면 code → easy) |
| 경로만 있고 의도가 불분명 | "코드를 정리할까요(code), 개발자용 글(post), 비개발자용 글(easy) 중 무엇을 만들까요?" 한 줄로 묻는다 |

경로가 없으면 현재 작업 폴더를 대상으로 하되, 무엇을 대상으로 잡았는지 먼저 한 줄로 알린다.

스크립트 경로: 이 SKILL.md 와 같은 폴더의 `scripts/outline.py`. 실행은 `python <스킬폴더>/scripts/outline.py <경로> [--check | --json]`. Python 3.8 이상이면 추가 설치 없이 돈다.

## code 모드

### 1. 준비
- 프로젝트가 실제로 쓰는 Python 버전을 확인한다. 타입 문법이 버전마다 달라서, 틀리면 실행 순간 에러가 난다.
  기본 `python --version` 만 믿지 말고, 프로젝트 CLAUDE.md·README·`.python-version`·폴더 안 `.conda`/`venv` 에 다른 환경이 적혀 있으면 그 버전을 따른다. 알 수 없으면 기본 `python` 버전 기준으로 쓰고 그 가정을 보고에 적는다.
- `references/python-style.md` 를 읽는다. 모든 형식 규칙과 완성 예시가 거기 있다.
- 기존 파일을 정리하는 경우, 대상 파일과 그 파일을 import 하는 쪽을 먼저 읽는다. 함수 이름이나 시그니처를 바꾸면 호출하는 쪽이 깨지기 때문이다.

### 2. 작성 / 정리
- **새 코드**: 처음부터 규칙대로 쓴다.
- **기존 코드 정리**: 바꾸는 건 형식뿐이다 — 파일 헤더, 섹션 구분선, 타입 힌트, docstring, import 순서, 상수 `Final`.
  **동작은 바꾸지 않는다.** 로직 개선, 함수 분리, 이름 변경이 필요해 보이면 고치지 말고 끝에 "제안"으로 따로 적는다. 정리 요청에 몰래 로직 변경이 섞이면 사용자는 diff 를 보고도 무엇이 바뀌었는지 믿을 수 없게 된다.
- `TODO(human)` 이 붙은 함수는 사용자가 직접 구현할 자리다. 타입 힌트와 docstring 은 붙여도 되지만, 본문은 비워둔 상태 그대로 둔다.

### 3. 검증
1. `python <스킬폴더>/scripts/outline.py --check <파일들>` → 모든 파일이 `[OK]` 가 될 때까지 고친다. 남겨둔 항목이 있으면 이유를 적는다.
2. `python -m py_compile <파일들>` → 문법 확인.
3. `mypy` 나 `pyright` 가 이미 설치돼 있으면 돌린다. 없으면 설치하지 말고 "타입 검사기 없음 — 정적 타입 검증은 못 함" 이라고 보고한다.
4. 가능하면 실제로 실행하거나 import 해본다 (`python -c "import auth"`). Streamlit 앱처럼 띄워야 하는 건 import 확인까지만 하고 그 사실을 적는다.

### 4. 보고
- 바꾼 것을 파일별로 짧게 정리한다 (헤더 추가, 타입 N곳, docstring N개, 섹션 구성).
- `--check` 결과와 검증 결과를 그대로 보여준다.
- 따로 적은 "제안"이 있으면 마지막에.

## post 모드

### 1. 재료 모으기
1. `python <스킬폴더>/scripts/outline.py <대상>` 으로 뼈대(제목·섹션·함수표·TODO)를 뽑는다.
2. 대상 코드를 **직접 끝까지 읽는다.** 뼈대는 목차일 뿐이고, "왜 이렇게 했는지" 는 코드 본문과 주석에 있다.
3. 같은 폴더의 README, requirements.txt, CLAUDE.md, 실행 로그가 있으면 함께 본다 (실행 방법·사용 기술의 근거).
4. `references/post-guide.md` 를 읽는다. 템플릿과 게시처별 주의점이 있다.

뼈대 출력에 `?`(타입 누락)나 "docstring 없음"이 많으면, 글은 코드를 읽고 추론해서 쓰되 끝에 "code 모드로 먼저 정리하면 다음 글은 더 정확해져요" 라고 한 줄 권한다. post 모드에서는 소스 파일을 고치지 않는다.

### 2. 쓰기
- `references/post-guide.md` 의 기본 템플릿을 따른다. 기본은 노션·Velog 공용 마크다운.
- 사용자가 "GitHub 블로그", "Jekyll", "깃허브 페이지" 라고 하면 가이드의 GitHub 블로그 추가 규칙(front matter, 파일명, Liquid 이스케이프)을 적용한다.
- 독자는 **이 코드를 처음 보는 사람 + 몇 달 뒤의 나** 다. 함수표로 큰 그림을 먼저 주고, 핵심 코드 2~4곳만 발췌해 "무엇을 / 왜" 를 쓴다.
- 문체: 학습 기록 톤의 평서문 ("~했다", "~한다"). 사용자가 다른 톤을 원하면 따른다.

### 3. 지어내지 않는다
블로그 글은 나중에 그대로 믿고 다시 보는 기록이다. 그럴듯한 거짓이 섞이면 기록의 가치가 사라진다.
- 실행 결과·출력·성능 수치는 사용자가 줬거나 실제로 실행해서 확인한 것만 쓴다. 없으면 `<!-- 📸 실행 화면 캡처 넣기 -->` 자리 표시만 남긴다.
- 코드에 없는 기능을 "구현했다" 고 쓰지 않는다. `TODO` 나 미구현 부분은 "다음에 해볼 것" 으로 보낸다.
- 라이브러리 내부 동작을 설명할 때 확실하지 않으면 그 부분은 짧게 줄인다.

### 4. 공개 전 점검과 저장
- 가이드의 "공개 전 점검" 항목(API 키, 개인 경로, 이메일 등)을 확인하고, 바꾼 게 있으면 보고한다.
- 저장 위치: 사용자가 지정하지 않으면 `<대상 폴더>/posts/<YYMMDD>_<주제>.md` (GitHub 블로그면 `YYYY-MM-DD-slug.md`). 같은 이름 파일이 있으면 덮어쓰기 전에 묻는다.
- 터미널에는 글 전체를 다시 출력하지 않는다. 저장 경로, 글 목차(## 제목들), 점검에서 바꾼 것, 자리 표시로 남긴 곳만 알려준다.

## easy 모드

독자가 **코딩을 전혀 모르는 사람**인 분석 글. 블로그 방문자, 비개발 동료, 가족에게 "내가 뭘 만들었는지" 보여주는 글이다.

1. **재료 모으기**: post 모드 1단계와 같다 (`outline.py` 로 뼈대 → 코드 끝까지 읽기 → README 등). 대신 가이드는 `references/easy-guide.md` 를 읽는다. 게시처별 형식(노션·Velog·GitHub)은 `references/post-guide.md` 의 "게시처별 차이" 를 그대로 따른다.
2. **쓰기**: `easy-guide.md` 템플릿을 따른다. 핵심은
   - 큰 그림(일상 비유 하나 + 매핑 표) → 실제 값으로 따라가는 시나리오 → 부품별 설명 순서. 큰 그림을 먼저 줘야 세부 설명이 어디에 붙는지 독자가 길을 잃지 않는다.
   - 각 부품의 "넣는 것 → 나오는 것" 은 함수 타입을 가이드의 번역표로 옮겨 쓴다.
   - 코드 블록은 부품당 3~10줄만, 바로 아래에 "쉽게 말하면" 으로 풀어준다.
   - 요청에 독자 역할(기획자, 팀장, 디자이너 등)이 나오면, 그 독자가 **읽고 나서 정하거나 챙길 것** 을 질문형 체크리스트 섹션으로 넣는다 (가이드의 "독자 역할에 맞추기"). 이해시키는 데서 끝나면 그 독자에게는 반쪽짜리 글이다.
3. **지어내지 않는다**: post 모드 3단계 규칙과 같다. 쉬운 말로 쓰더라도 사실이 틀리면 안 된다. 비유가 실제 동작과 다른 지점은 글 안에서 짚는다.
4. **공개 전 점검과 저장**: post 모드 4단계와 같다. 파일명은 `<YYMMDD>_<주제>_easy.md` 로 해서 post 모드 글과 구분한다.

## all 모드

code 모드를 끝까지(검증 포함) 마친 뒤 post 모드를 시작한다. code 모드 결과를 사용자가 확인할 수 있게 둘 사이에 한 번 요약을 보여주고, 바로 이어서 post 를 진행한다.
